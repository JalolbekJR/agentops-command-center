# Local Demo Boundary

AgentOps Command Center is currently a deterministic frontend control-plane prototype. This document explains what works locally, what is intentionally simulated, and what the future backend must enforce.

## What is implemented now

The current app includes:

- Next.js, React, and TypeScript frontend
- Premium responsive app shell
- Role-aware local navigation
- Local restricted-route behavior
- Dashboard, Agents, Built-in Agents, Agent Builder, Workflows, Runs, Approvals, Evaluations, Risks, Browser QA, Audit, Connectors, Plans, Setup, Settings, and Owner Control surfaces
- Deterministic mock data
- Dark/light theme state
- Simple/Professional view mode state
- Playwright route, access, console, responsive, theme, mode, and screenshot coverage

## What is intentionally local and deterministic

The prototype uses local state and deterministic data so reviewers see the same product story on every run.

Local deterministic behavior includes:

- Role selection
- Sidebar visibility and route gates
- Theme and view mode preferences
- Seeded agents, runs, risks, approvals, evaluations, and audit records
- Screenshot artifacts generated by Playwright

## What is not implemented yet

The current app does not include:

- Real auth provider
- Production session model
- Database writes
- Server-side RBAC enforcement
- External connector calls
- Live agent execution
- Payment provider
- Customer data
- Secrets
- Production deployment

## Why backend enforcement is later

The frontend prototype proves the product model before adding infrastructure. That keeps scope controlled and makes the safety boundary visible.

Backend enforcement is intentionally scoped to the roadmap because production permissions, approval decisions, audit events, connector writes, and secret handling must happen server-side.

## Role switcher boundary

The role switcher demonstrates how product surfaces change by role. It is not a production security boundary.

Future backend routes must enforce:

- Who can read each route
- Who can create or modify agents
- Who can decide approvals
- Who can inspect sensitive tool output
- Who can access Owner Control
- Who can change roles, policies, plans, or connector settings

## Data boundary

All current records are deterministic mock data. The project does not use customer data, private URLs, real emails, payment records, or live secrets.

Future persistence should use PostgreSQL or an equivalent relational store with project-scoped access, stable IDs, indexes, retention policies, and audit-critical records.

## Security boundary

The current UI prevents restricted content from rendering for roles that cannot access it, but the browser cannot be trusted as the final authority.

Future backend security must include:

- Server-side RBAC
- Authenticated sessions
- Policy checks on every sensitive read and write
- Append-only audit events
- Secret references instead of raw secret values
- Redaction for sensitive tool inputs and outputs
- Environment boundary checks
- Rate limits and abuse controls

## Connector boundary

Connector pages currently model future connection paths. They do not call external services.

Future connector enforcement must include:

- Deny-by-default connector policy
- Allowlisted targets
- Hashed connector tokens
- Schema validation
- Replay protection for inbound events
- Secret references stored outside client state
- Audit records for connector changes
- Worker isolation for sensitive execution

## Payments and plans boundary

Plans model future commercial packaging. The current app does not process payments, create subscriptions, call billing portals, or enforce usage server-side.

Future billing work should keep payment provider logic behind explicit backend scope and approval.

## Future enforcement path

The production path should add:

1. Auth and workspace membership
2. Server-side RBAC
3. PostgreSQL persistence
4. API route validation
5. Transactional approvals
6. Append-only audit events
7. Connector policies and allowlists
8. Secret references
9. Queue/worker execution
10. Observability and production hardening
